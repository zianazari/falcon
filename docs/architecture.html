Falcon architecture

Falcon has four main parts and a web console. This page shows what each part is built with, where it runs, which identity connects it to the next part, and how data moves between them.

Current state (November 2026): the GCP deployment has been torn down to avoid idle cost, so the map shows the system as designed and as tested. It can be recreated with Terraform. The local stack runs with make up, and CI runs on every push.

How the parts connect

The system stores no key files. Each connection uses a specific identity, and access is scoped as narrowly as the service allows.

Data flow

Flow 1: from a risky action to an alert

This flow was tested on a real GCP project. Making a bucket public raised an alert 1.6 seconds after the audit event.

  1. Someone acts in GCP, for example by granting allUsers read access to a bucket.
  2. GCP records the action in Cloud Audit Logs.
  3. The log sink sends the entry to the Pub/Sub topic.
  4. Pub/Sub pushes it to Cloud Run with an OIDC token.
  5. The pipeline processes it as shown in the figure below.
  6. The alert is stored in the alerts table and written to the Cloud Run log. With a webhook configured, it also goes to Slack.

Flow 2: from a vulnerability to an issue

This logic is tested against recorded data. It has not yet run against live GitHub repositories.

  1. The triager fetches Dependabot and code-scanning alerts.
  2. For each CVE it checks the EPSS exploit probability and the CISA KEV catalog.
  3. It calculates a score from 0 to 100, a priority from P1 to P4, and a fix deadline.
  4. It finds the owning team from CODEOWNERS.
  5. It decides what to do with the issue: create, update, nudge, reopen or close.
  6. If a P1 or P2 passes its deadline, the CI gate fails.

Flow 3: from stored data to the console

  1. The browser requests /api/alerts and similar routes.
  2. Vite passes the request to the console API.
  3. In GCP mode the server reads BigQuery and the other APIs, and caches each response for 30 seconds.
  4. The page refreshes every 60 seconds.

Each console query creates an audit log entry, which comes back through flow 1. BigQuery events therefore keep rising in the Events page while the console is open in GCP mode.

Flow 4: from code to GCP

  1. Terraform creates the resources.
  2. Docker builds the pipeline image for linux/amd64. Tests and rule fixtures run during this build.
  3. The image goes to Artifact Registry, and a new Cloud Run revision takes over.

The tested deployment did these steps by hand. With its variables set, deploy.yml does the same without keys.

Not yet active or tested

  • Only the ci workflow runs. triage and deploy skip until their variables are set.
  • Slack delivery is untested, because no webhook has been configured.
  • The triager has not run against a live repository, so the console shows demo data.
  • Only the public-bucket rule was tested by a real action on GCP. The other five rules are verified by fixtures and the local attack replay.
  • Terraform state is local and has not moved to a shared bucket.
  • GCP keeps a deleted Workload Identity pool for about 30 days, which can block a new apply until it is undeleted or renamed.
